# Minimal booking design

## Learning objective

Booking exists to teach how an authenticated identity owns application data.
It is not an attempt to implement a complete travel-sales system.

The first slice adds one relationship:

```text
Keycloak user subject → Booking → Journey
```

## Minimal persisted model

`Booking` contains only:

| Field | Database type | Purpose |
| --- | --- | --- |
| `Id` | `uuid` | Primary key generated by the application. |
| `JourneyId` | `uuid` | Required foreign key to `Journey`. |
| `UserSubject` | `varchar(255)` | Owner from the validated JWT `sub` claim. |
| `BookedAtUtc` | `timestamptz` | Server-controlled creation instant. |

One journey can have many bookings. One authenticated user can have many
bookings, but only one booking for a particular journey. A unique constraint
on `(UserSubject, JourneyId)` enforces that rule at the database boundary.

Deleting a journey with bookings will be restricted. Historical user activity
must not disappear because a parent record is removed.

## Identity boundary

The first slice does not create an `ApplicationUser` table. Keycloak remains
the identity authority, and `UserSubject` stores the stable subject identifier
from the validated access token.

The booking request will contain only the selected journey identifier:

```json
{
  "journeyId": "00000000-0000-0000-0000-000000000000"
}
```

It must not accept `userSubject`, username, or email from the browser. The
backend derives ownership from `HttpContext.User` after token validation. This
prevents a caller from creating a booking on behalf of another user.

## Deliberately deferred behavior

The initial model excludes:

- passengers and tickets;
- prices, fares, and payments;
- seat numbers and capacity;
- cancellation and booking status;
- an application-local user profile;
- administrator booking operations.

If cancellation becomes the next learning objective, a status field will be
added through a later migration. That will demonstrate safe schema evolution
instead of adding speculative fields now.

## Planned implementation slices

1. Add the entity, relationship, constraints, and migration.
2. Add `POST /api/bookings`, deriving ownership from the `sub` claim.
3. Add `GET /api/bookings/mine`, filtering by that same claim.
4. Add the smallest React interface needed to exercise both operations.

Each slice will be reviewed before the next begins.
